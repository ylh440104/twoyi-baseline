# 基座功能完成度与实测缺口

本表按“实现 / 云端验证 / 设备验证”三级如实标注。**设备验证一栏目前全部为“否”**：专用 ARM64 runner 未接入（workflow 需要 `workflow_dispatch` 且 `device_smoke=true`，且要求自托管 runner 标签 `twoyi-dedicated-test-device`）。因此任何“已通过”只代表代码与云端构建/主机回归通过，不代表真机行为。

构建与回归证据统一来自公开仓库 https://github.com/ylh440104/twoyi-baseline 。

## 一、本体与容器基座

| 功能 | 实现 | 云端验证 | 设备验证 | 关键缺口 |
|---|---|---|---|---|
| 启动（ROM 预检、暂存切换、恢复） | 是 | 是（ROM 归档预检、事务恢复回归、APK 构建） | 否 | 真机首次安装/替换/解包耗时与失败清理 |
| 退出/关机（停进程组、发布停止态） | 是 | 是（状态机回归） | 否 | 真机跨进程组残留、服务回收 |

## 二、与最新版 0.7.5 的结构性差距

| 项目 | 状态 | 说明 |
|---|---|---|
| 多进程 `:guest0`…`:guest3` | 骨架 | 四个服务已声明在对应进程但 `enabled="false"`；来宾仍跑在主进程。渲染器/init/控制服务需要按进程重建才能启用 |
| 前台服务类型 `specialUse` | 未实现 | 需要 compileSdk 34，本树为 31 |
| 后台屏 `HostBackdropActivity` | 未实现 | 需要在 `:guest0` 里持有 Surface 并驱动后台任务 |
| ROM 载体 `rootfs.tar.zst` | 未实现 | 最新版只接受 direct USTAR + zstd；本树仍是 `rootfs.7z` + libp7zip |
| Binder 控制面（`INSTANCE_ID` 选槽） | 未实现 | 本树仍是抽象 socket `TWOYI_SOCK` 文本命令。该名称编译在 ROM 的 loader 里，**不能按槽改名**，否则来宾连不上监听、启动永远收不到完成通知；因此当前同名 socket 意味着同一时刻只能有一个来宾在跑。真正的多实例必须先做 Binder 或改来宾侧 |
| Compose + Material 3 界面 | 未实现 | 最新版整体重写；本树是 AppCompat + XML |
| 四实例真实并存 | 未实现 | 文件层面（rootfs、日志、输入设备）已按槽隔离并有回归；socket 名必须共用，所以并存需要新的控制通道，且同一进程仍是单来宾 |

## 三、为什么硬件桥接停在证据阶段

`docs/HAL_BRIDGE.md` 记录了从 0.5.4 配套 ROM 取得的字符串证据：audio/lights/vibrator/sensors/gps 连接抽象 socket `twoyi_hal`，camera 走独立 `twoyi_camera_transport`，hwcomposer 走渲染器共享内存。缺少帧头长度、版本字段取值与结构体布局，绑定却不按协议应答会让来宾 HAL 阻塞，比当前自带降级（如传感器 0 个）更差。因此**不绑定**，只记录连接。

## 四、下一步可做但未做

1. 让 `:guestN` 真正承载来宾（渲染器、init、控制服务按进程重建），这是多实例并存的唯一正确路径。
2. zst ROM 换代：新原生解包接口 + 预检 + 事务回归。
3. Compose 界面重写：需要先升级 AGP/Kotlin 并引入 Compose 编译器，属于独立阶段。
4. 设备验收：任意一项要变成“设备验证=是”，都必须先接入 ARM64 runner。
